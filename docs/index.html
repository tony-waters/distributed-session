Distributed Session Architecture

Three instances of each service sit behind a round-robin load balancer with no sticky sessions. Nothing about a logged-in user lives in a service process — the Session and the Cart both live in Redis — so any instance can answer any request, and consecutive requests for one session deliberately land on different ones.

What makes the instances interchangeable

session-contract

One serializer, two services

Spring Session's default JDK serialization can't be read across two services' classpaths, so a shared auto-configuration module pins both to a JSON serializer and one Redis namespace. It also owns SessionAttributes.USERNAME, the single key login-service writes and cart-service reads.

cart-service

Atomic appends, not read-modify-write

The Cart is its own Redis list, not a Session attribute. A single RPUSH per add means two concurrent adds on two different instances can't clobber each other the way rewriting a whole session attribute would. The key's TTL is reset to the session's remaining lifetime on every add.

login-service

Login always mints a fresh Session

Any session presented on /login is invalidated before a new one is created — the glossary rule that Login never reuses a Session, which also closes session fixation: a pre-set cookie can never become an authenticated one.

cart-service

Authentication ahead of every endpoint

A servlet filter scoped to /cart/* rejects any request whose session lacks the username, so a newly added endpoint can't skip the check. Missing, expired and unknown sessions all get the same generic 401 — no detail to probe. The scope matters: unscoped it would also reject the unauthenticated health probe.

frontend

Same origin, so no CORS

nginx serves the React build and proxies /api/* to the services on port 3000, so the SESSION cookie is first-party and cross-site POSTs stay blocked by SameSite=Lax. The bare 8080/8081 entrypoints are untouched, so curl and k6 still drive the services directly.

observability

X-Instance-Id is a label, not a route

A highest-precedence filter stamps every response — 401s and health probes included — with the instance that produced it, before the chain runs so a short-circuiting filter can't commit the response without it. The frontend's request log reads only this header.
